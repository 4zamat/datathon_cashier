# cashier-violation-detector

Сервис для кейса ForteBank на Datathon: сотрудник службы безопасности загружает видео работы кассира и получает список возможных нарушений с таймкодами, кадрами и ссылками на пункты правил.

**Сейчас готова инфраструктура сервиса, но настоящее распознавание ещё предстоит сделать.** Включён `DummyPipeline`: он извлекает кадры с частотой 2 fps и всегда возвращает одно **фиктивное** нарушение с реальным JPEG из середины записи. В справочнике находится демонстрационное правило. Такой результат проверяет работу приложения, но ничего не говорит о действиях кассира.

Быстрые переходы: [задачи команды](#3-раздельные-задачи-для-команды) · [план работы](#4-план-работы-по-порядку) · [Brev](#5-когда-и-как-используем-nvidia-brev) · [критерии готовности](#6-как-понимаем-что-проект-готов) · [запуск](#8-запуск) · [API](#9-api).

## 1. Что мы делаем простыми словами

Итоговый сценарий:

1. Пользователь открывает страницу, вводит API-ключ и выбирает файл `.mov` размером примерно 30 МБ.
2. Сервис принимает файл и выдаёт номер задания — `job_id`.
3. Модель анализирует видео на нашем сервере. Страница проверяет статус каждые 2 секунды.
4. Пользователь получает «Нарушения не обнаружены» либо список возможных нарушений.
5. Для каждого события показаны время в секундах от начала видео, описание, 1–3 настоящих кадра и документ с точным пунктом.
6. Загруженное видео удаляется после обработки. Результат с кадрами сохраняется.

Система помогает человеку проверить запись. По изображению нельзя установить то, чего на нём не видно: например, правильность проводки во внутренней банковской системе. В описание должны попадать только наблюдаемые действия.

```text
Видео → веб-страница → FastAPI → очередь → анализ видео
                                             ↓
                              события + таймкоды + кадры
                                             ↓
                              правила из rules/rules.yaml
                                             ↓
                                 JSON → веб-страница
```

**Пайплайн** — последовательность действий, превращающая видео в результат. **Обучение** — настройка модели на примерах. **Инференс** — применение уже готовой модели к новому видео. **Baseline** — первая работающая модель, с которой сравниваем улучшения.

## 3. Раздельные задачи для команды

В начале работы впишите конкретного ответственного для каждой роли. Результат задачи — файл, работающий код или отчёт, который другой участник может проверить.

| Роль | Что конкретно сделать | Что сдать | Когда задача готова |
|---|---|---|---|
| Нормативные акты | Для выбранных событий найти применимый документ, проверить редакцию, пункт и связь с видимым действием | `docs/rules_sources.csv` и обновлённый `rules/rules.yaml` | Каждая категория имеет проверяемый источник и понятный признак на видео |
| Данные и разметка | Просмотреть записи, проверить исходные метки, отметить события и сомнения, разделить данные | `data/labels.csv`, `data/train.csv`, `data/val.csv`, `data/events.csv` | Все пути читаются, метки проверены, одна запись и её фрагменты не попали в обе выборки |
| Интерфейс и дизайн | Доработать страницу в стиле ForteBank, подключить состояния API, показать доказательства и правила | Изменения в `static/`, скриншоты основных состояний | Загрузка → ожидание → результат работает; ошибки не выглядят как отсутствие нарушений |
| ML и интеграция | Сделать baseline, измерить качество, при необходимости дообучить на Brev, подключить к сервису | `pipeline/real.py`, конфигурация, веса, отчёт о качестве | Результат получен реальной моделью, воспроизводится и укладывается в бюджет времени |
| Проверки и развёртывание | Проверить Docker, ошибки, таймаут, офлайн-запуск и доступность сервера | Отчёт `docs/acceptance.md`, инструкция запуска, адрес API | Другой участник запускает систему по README и успешно проверяет API извне |

Имена новых файлов выше — **планируемые результаты работ**, сейчас этих файлов может не быть. Видео, разметка и веса остаются вне Git согласно `.gitignore`; в отчётах фиксируем версии и расположение артефактов.

Если участников трое: первый берёт нормативы и данные, второй — интерфейс и проверки, третий — ML, Brev и интеграцию. Если четверо, данные лучше выделить отдельному человеку. Формат API и общие названия типов нарушений согласует ответственный за интеграцию.

## 4. План работы по порядку

### Этап 1. Зафиксировать, какие события ищем

**Ответственные: нормативы + данные + ML.**

1. Просмотреть доступные обучающие видео и исходную разметку организаторов.
2. Составить список действий, которые действительно различимы на записи.
3. Для каждого предполагаемого нарушения найти подтверждающий пункт правила. Само по себе необычное действие ещё не означает нарушение.
4. Присвоить согласованные идентификаторы `type`. Они должны совпадать в разметке, модели и YAML.
5. Для неоднозначных случаев записать, какой информации не хватает для вывода.

В таблице источников нужны поля: `type`, название и дата документа, пункт, точная цитата, URL источника, дата проверки, наблюдаемый признак и ограничения. Не переносим номера актов из примеров или переписки без проверки полного документа и его применимости.

В `rules/rules.yaml` у каждой категории остаются **только** `document`, `clause`, `summary`: это текущая схема приложения. Цитаты, URL и примечания храним в отдельной таблице источников.

**Готово, когда:** для каждой выбранной категории команда одинаково понимает, что должно быть видно на видео и каким пунктом это обосновывается. Неподтверждённые категории остаются в списке вопросов.

### Этап 2. Подготовить данные и проверочную выборку

**Ответственный: данные. Можно выполнять одновременно с этапом 1.**

1. Поместить исходные записи в `data/videos/`. Не использовать служебные `data/uploads/` и `data/work/`.
2. Проверить, что все видео открываются; записать длительность, повреждения и особенности ракурса.
3. Сохранить исходные метки организаторов. Исправления и сомнения отмечать отдельно, чтобы не потерять происхождение разметки.
4. Подготовить CSV для оценки: `video,has_violation,timecode_sec`, одна строка на видео. Подробности нескольких событий и типы хранить отдельно в `data/events.csv`.
5. Зафиксировать обучающую и проверочную выборки в `data/train.csv` и `data/val.csv` с той же схемой. Разделять по исходным записям; связанные фрагменты и дубли держать в одной группе.
6. По возможности оставить в проверочной выборке и нарушения, и нормальные действия. При малом количестве примеров явно указать ограничения оценки.

Проверочную выборку не используем для обучения; тестовые видео организаторов не включаем в обучение или подбор настроек. Метки «есть нарушение + секунда» не являются разметкой объектов рамками: если выбранная модель требует рамки, их подготовка станет отдельной задачей.

**Готово, когда:** другой участник может открыть любой пример из CSV, понять метку и воспроизвести разделение данных.

### Этап 3. Получить первый настоящий результат модели

**Ответственный: ML. Нужны согласованные категории и данные из этапов 1–2.**

1. Выбрать предобученную модель, которую можно запускать локально и использовать по её лицензии. Зафиксировать название, версию, требования к памяти и способ получения весов.
2. Реализовать первую версию `pipeline/real.py` по интерфейсу `Pipeline`: подготовка кадров или коротких фрагментов → определение событий → объединение повторных срабатываний → выбор таймкода и 1–3 кадров.
3. Возвращать только согласованные `type`, описание наблюдаемого действия и реальные кадры исходной записи. Пункты правил добавит сервер из YAML.
4. Прогнать baseline на фиксированной проверочной выборке через `scripts/eval.py`.
5. Отдельно измерить время полного анализа и разобрать пропуски, ложные срабатывания и ошибки категории. Текущий eval не считает точность классификации типов и не измеряет скорость.
6. Сохранить результат в `docs/model_report.md`: версия модели, выборка, настройки, метрики, время, примеры ошибок.

**Готово, когда:** есть воспроизводимый результат настоящей модели и понятно, что именно мешает качеству. Дообучение планируем по этим ошибкам; оно не гарантирует улучшения само по себе.

### Этап 4. Провести GPU-эксперименты и при необходимости дообучение

**Ответственный: ML / Brev.** Первый baseline тоже можно запускать на Brev, если локального GPU недостаточно. Порядок аренды описан ниже.

1. Подготовить воспроизводимый запуск: конфигурацию модели, пути к данным, зависимости и команду эксперимента. Если нужно обучение — написать обучающий скрипт; сейчас его в проекте нет.
2. На коротком прогоне проверить чтение данных, использование GPU, сохранение весов и возможность загрузить их обратно.
3. При дообучении использовать только обучающую часть. Сохранять настройки и версии каждого эксперимента.
4. Сравнить baseline и новую версию на одной проверочной выборке: recall, precision, ошибка таймкода, ошибки типов и время обработки.
5. Выбрать версию для интеграции по измерениям. Если дообучение не помогло, оставить более удачный baseline.
6. Скопировать итоговые веса, конфигурацию и отчёт в доступное команде хранилище. Указать способ восстановления модели на чистой машине.

**Готово, когда:** выбранная версия загружается из сохранённых файлов и повторяет заявленные результаты.

### Этап 5. Подключить модель и завершить интерфейс

**Ответственные: ML + интерфейс. Интерфейс можно готовить на заглушке ещё с этапа 1.**

1. Подключить выбранные веса в `pipeline/real.py`, проверить контракт `Pipeline.analyze(video_path) -> Result` и переключить `PIPELINE_CLASS` сервиса.
2. Проверить пустой результат, одно событие, несколько событий, ошибки чтения и неизвестный тип нарушения.
3. Измерить полный бюджет задачи: ожидание очереди, запуск процесса, загрузка модели и анализ. В текущей архитектуре модель загружается заново для каждого видео.
4. На странице показывать статус и прошедшее время. API пока не сообщает процент выполнения или этапы модели, поэтому вычисленные «проценты готовности» не выдаём за реальные.
5. Оформить карточки с читаемыми таймкодами, изображениями, описаниями и правилом из ответа API. Проверить узкий экран и длинные названия документов.
6. Показывать вердикт только при `done`. Для `failed` показывать ошибку; для `processing` — ожидание. При отправке учитывать успешный код **202**.

В текущем API нет `/health`. Если для интерфейса потребуется отдельная проверка доступности, её добавление нужно согласовать с владельцем бэкенда. Встроенный видеоплеер — дополнительная задача; при его добавлении нужно проверить воспроизведение реальных `.mov` в браузере.

**Готово, когда:** пользователь проходит весь путь через страницу и видит результат реальной модели, совпадающий с JSON API.

### Этап 6. Проверить сборку и подготовить сдачу

**Ответственные: проверки + интеграция.**

1. Запустить автотесты и собрать Docker-образ с нужными зависимостями.
2. Подготовить все веса и файлы модели заранее. Запустить анализ при отключённом исходящем интернете; проверить, что нет скачиваний и обращений к внешним AI API.
3. Проверить реальный `.mov` около 30 МБ, нормальную запись, нарушение, повреждённое видео, неверный ключ, заполненную очередь и таймаут.
4. Проверить удаление загруженных видео, восстановление JSON после перезапуска и отсутствие зависшего процесса после таймаута.
5. Развернуть сервис на выбранном сервере и проверить оба API-метода с другого компьютера. Публичная ссылка должна работать с `X-API-Key` без дополнительного входа в консоль провайдера.
6. Измерить время от начала загрузки до получения результата через публичный адрес. Бюджет сервиса — 270 секунд после постановки в очередь; общий лимит кейса — 5 минут, поэтому сетевую загрузку тоже нужно учитывать.
7. Подготовить короткую демонстрацию: обычная запись, запись с событием, кадры и правило, а также честный отчёт о качестве и ограничениях.

**Готово, когда:** другой участник запускает проект по README, проверяет публичный API и получает воспроизводимый результат на согласованной версии модели.

## 5. Когда и как используем NVIDIA Brev

[NVIDIA Brev](https://brev.nvidia.com/) даёт арендуемую виртуальную машину с GPU. На ней запускаем свой код и свою модель: сначала проверку baseline, затем обучение, если оно нужно. GPU выбираем под память модели и бюджет команды после подготовки эксперимента. [Описание GPU-инстансов NVIDIA](https://docs.nvidia.com/brev/concepts/gpu-instances).

До аренды должны быть готовы список необходимых файлов, команда запуска, модель-кандидат и лимит расходов. Перед переносом банковских видео нужно закрыть вопрос организаторам: **допускается ли хранить и обрабатывать обучающий датасет на арендованной приватной GPU-машине?** В доступном ТЗ есть запрет внешних облачных AI API при анализе, но явного разрешения на такой перенос обучающих данных мы не подтвердили.

Порядок работы:

1. Открыть консоль Brev → **GPUs → Create Instance**.
2. Выбрать доступный GPU, образ окружения и размер диска; проверить текущую стоимость.
3. Подключиться через SSH или выбранное окружение Jupyter. Проверить Python 3.11 и совместимость зависимостей проекта.
4. Разместить код, разрешённые данные и файлы эксперимента в рабочем каталоге `/home/ubuntu/workspace`.
5. Запустить короткую проверку, затем основной эксперимент; сохранить веса, конфигурацию и метрики.
6. Скопировать нужные результаты до остановки машины. В остановленном состоянии вычисления не оплачиваются, но хранение может оплачиваться; удаление инстанса уничтожает его данные.

Шаги создания и доступа: [официальная инструкция консоли](https://docs.nvidia.com/brev/guides/console-reference). Сохранность данных и оплата при остановке: [жизненный цикл инстанса](https://docs.nvidia.com/brev/concepts/gpu-instances).

После обучения веса нужно подключить к нашему сервису и проверить скорость на сервере сдачи. Аренда GPU для обучения сама по себе не решает вопрос оборудования для обработки новых видео. Нужен отдельный выбор: на какой машине будет постоянно работать API.

## 6. Как понимаем, что проект готов

- [ ] На новых видео работает настоящая модель; демонстрационный результат не используется для оценки качества.
- [ ] Для каждой выдаваемой категории проверены документ, пункт и наблюдаемый признак.
- [ ] Зафиксированы проверочная выборка, версия модели, recall, precision, ошибка таймкода и время работы.
- [ ] Проверены категории событий; ограничения текущего eval описаны в отчёте.
- [ ] Оба API-метода защищены ключом; кадры и структура ответа соответствуют контракту.
- [ ] Обработка укладывается в лимит; таймаут освобождает воркер и удаляет временные файлы.
- [ ] Ошибка обработки не отображается как «нарушений нет».
- [ ] Сборка воспроизводится, модель работает без внешних AI API и скачивания файлов при анализе.
- [ ] Страница и API доступны проверяющим; запросы протестированы извне.
- [ ] Есть инструкция получения весов, запуска, результаты проверок и демонстрация.

## 8. Запуск

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export API_KEY='replace-with-a-long-random-secret'
export HF_HUB_OFFLINE=1
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:API_KEY = 'replace-with-a-long-random-secret'
$env:HF_HUB_OFFLINE = '1'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

Страница: <http://localhost:8000/>. OpenAPI: <http://localhost:8000/docs>. Введите ключ в форму; браузер не сохраняет его в localStorage, cookies или URL. Оба API-метода проверяют `X-API-Key`; отсутствующий или неверный ключ даёт `401`, в том числе до разбора multipart.

Используйте **ровно один процесс Uvicorn** и один экземпляр приложения на каталог `DATA_DIR`: очередь и кэш статусов находятся в памяти. Не используйте `--workers 2` и не разделяйте каталог данных между несколькими контейнерами.

## 9. API

Пример из ТЗ (замените адрес и ключ):

```bash
curl -X POST https://team.example.kz/api/v1/analyze \
  -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
```

Локальная проверка:

```bash
curl -X POST http://localhost:8000/api/v1/analyze \
  -H "X-API-Key: $API_KEY" -F "file=@video_017.mov"
# HTTP 202: {"job_id":"..."}

curl http://localhost:8000/api/v1/jobs/JOB_ID \
  -H "X-API-Key: $API_KEY"
```

В PowerShell используйте `curl.exe` и `$env:API_KEY` вместо `$API_KEY`.

Пока результат ещё неизвестен:

```json
{"job_id":"...","status":"processing","verdict":"no_violation","violations":[],"error":null}
```

Успешное завершение:

```json
{
  "job_id": "...",
  "status": "done",
  "verdict": "violation",
  "violations": [{
    "type": "demo_violation",
    "timecode_sec": 2.0,
    "description": "ДЕМОНСТРАЦИЯ: фиктивное нарушение...",
    "rule": {
      "document": "Демонстрационный регламент (не нормативный акт)",
      "clause": "DEMO-1"
    },
    "evidence_frames": [{"timestamp_sec": 2.0, "image_base64": "<JPEG base64>"}]
  }],
  "error": null
}
```

Пайплайн без событий возвращает `done`, `no_violation`, `[]`. При сбое: `failed`, пустой список и текст `error`. **Вердикт нужно интерпретировать только при `status=done`.** Для `processing` и `failed` поле содержит техническое значение `no_violation`, чтобы сохранять строго заданный enum; это не результат проверки. Страница сначала проверяет статус и не показывает вердикт при ошибке или ожидании. Поле `image_base64` содержит только base64 JPEG без префикса `data:`; в каждом событии 1–3 кадра.

Другие коды: `404` — неизвестное задание; `415` — расширение не `.mov`; `400` — пустой файл; `413` — превышен лимит; `422` — нет поля `file`; `503` — очередь заполнена. Нечитаемое видео принимается как задание и затем получает `failed`. Файлы около 30 МБ укладываются в стандартный лимит 64 МиБ.

## 10. Очередь, таймаут и файлы

- Один поток читает FIFO-очередь. Одновременно работает не больше одного процесса анализа.
- Для каждой задачи поток запускает дочерний процесс через `spawn`. Это нужно, чтобы принудительно остановить зависший OpenCV или будущую модель: Python-поток безопасно остановить нельзя.
- Бюджет — **270 секунд после постановки в очередь**, включая ожидание, запуск процесса и анализ. Загрузка до получения `job_id` в него не входит. Очередь тоже видна как `processing`; по истечении бюджета задача получает `failed`.
- Видео сохраняется под случайным именем в `data/uploads/`, удаляется при завершении, ошибке, таймауте или штатном выключении. Частичная/отклонённая загрузка также удаляется. После аварийного завершения оставшиеся служебные файлы удаляются при следующем запуске.
- Статусы и кадры хранятся в памяти и `data/jobs/<job_id>.json`. JSON заменяется атомарно. После перезапуска готовые результаты восстанавливаются, незавершённые задания получают `failed`.
- `data/uploads/` и `data/work/` предназначены только для временных файлов сервиса; не кладите туда исходный датасет. JSON-результаты сохраняются до ручного удаления при остановленном сервисе; для больших объёмов понадобится политика хранения.
- Страница опрашивает API каждые 2 секунды, пока задание обрабатывается. После сетевой ошибки можно продолжить опрос того же задания.

## 11. Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `API_KEY` | обязательно | Секрет для обоих API-методов; пустое значение запрещено |
| `DATA_DIR` | `data/` внутри проекта | Каталог JSON и временных файлов |
| `RULES_PATH` | `rules/rules.yaml` внутри проекта | Справочник правил, читается при старте |

## 12. Замена пайплайна

Контракт находится в `pipeline/base.py`:

```python
from pathlib import Path
from pipeline.base import Pipeline, Result

class RealPipeline(Pipeline):
    def analyze(self, video_path: Path) -> Result:
        # Ваша локальная модель возвращает список app.models.Detection.
        return Result(violations=[])
```

Это пример интерфейса, а не реализация распознавания: возвращаемый пустой список всегда означает отсутствие событий. Файла `pipeline/real.py` пока нет. Когда реализуете класс, задайте `PIPELINE_CLASS=pipeline.real:RealPipeline` и перезапустите сервис. Для события нужны `type`, `timecode_sec`, `description` и 1–3 `EvidenceFrame`. Вердикт вычисляется из списка событий. Класс создаётся в отдельном процессе на каждое видео; загрузка будущей модели входит в бюджет, это следует учитывать при выборе весов.

Каждый `type` должен быть ключом `rules/rules.yaml`:

```yaml
demo_violation:
  document: "Демонстрационный регламент (не нормативный акт)"
  clause: "DEMO-1"
  summary: "Фиктивное событие для проверки сервиса."
```

`rule.document` и `rule.clause` добавляются сервером **только из YAML**. Сам пайплайн не может передать `rule`; неизвестный тип приводит к `failed`. Настоящие документы и пункты нужно внести после проверки источников. `summary` — краткое описание категории в справочнике; `description` — описание конкретного события.

DummyPipeline читает видео последовательно с OpenCV, выбирая кадры у отметок 0, 0.5, 1.0 секунды и далее. При переменной частоте используются временные метки декодера; при их отсутствии — индекс кадра / FPS. Для выбора середины выполняются два прохода без накопления всех кадров в RAM. JPEG уменьшается до 1280 пикселей по длинной стороне, если исходный кадр больше.

## 13. Оценка качества

### Куда положить датасет

Видео и разметку храним **локально в `data/` внутри папки проекта**. После клонирования репозитория эту папку нужно создать и заполнить отдельно: Git и сборка Docker её исключают.

```text
cashier-violation-detector/   # или datathon_cashier/ после git clone
  app/
  pipeline/
  data/
    videos/
      X-1.mov
      X-2.mov
      ...
      X-48.mov
    raw/
      open_labels.xlsx      # исходная таблица без изменений; CSV тоже хранить здесь
    labels.csv              # подготовленная разметка для scripts/eval.py
```

Копируйте папку `videos` целиком в `data/`, чтобы получилось `data/videos/`, а не `data/videos/videos/`. Исходную таблицу положите в `data/raw/`. Папки `data/uploads/` и `data/work/` используются сервисом для временных файлов и очищаются; исходные видео туда не кладите.

`scripts/eval.py` читает CSV с указанной ниже схемой. Он не читает XLSX и не преобразует исходные русские заголовки автоматически. При подготовке `labels.csv` нужно привести метку к `0`/`1`, таймкод — к секундам, а путь — к фактическому имени видео. Например, запись «1 минута 8 секунд» означает `68` секунд. Для отрицательной метки таймкод можно оставить пустым.

Имена должны совпадать точно, включая расширение и регистр: `X-3.mov`, `Х-3.mov` и `X-3.MOV` могут обозначать разные файлы. Визуально похожие латинская `X` и кириллическая `Х` имеют разные коды. После копирования видео обязательно сверьте пути из CSV с содержимым папки. Отсутствие строки в разметке не означает «без нарушения» — такие видео не добавляем в оценку с выдуманной меткой.

В GitHub отправляем код и инструкции. Датасет, реальные CSV, результаты с кадрами, веса и ключи остаются вне Git. Для обмена внутри команды используйте согласованное закрытое хранилище с учётом условий организаторов.

### Формат разметки и запуск оценки

Создайте `data/labels.csv` (одна строка на видео):

```csv
video,has_violation,timecode_sec
videos/video_001.mov,1,11.0
videos/video_002.mov,0,
```

Пути видео относительны каталогу CSV; можно использовать абсолютные пути. `has_violation`: `1`/`0` или `true`/`false`. Положительная метка требует конечный неотрицательный таймкод.

```bash
python scripts/eval.py
python scripts/eval.py --labels data/labels.csv --pipeline pipeline.dummy:DummyPipeline
```

Как читать результат:

| Метрика | Что означает |
|---|---|
| Recall | Какую долю видео с нарушениями система смогла обнаружить |
| Precision | Какая доля видео, отмеченных системой как нарушение, действительно содержит нарушение |
| Средняя ошибка таймкода | Насколько в среднем предсказанное время отличается от размеченного, в секундах |
| TP / FP / FN / TN | Верно найденные нарушения / ложные тревоги / пропущенные нарушения / верно распознанные нормальные видео |

Скрипт запускает пайплайн напрямую и печатает JSON: TP/FP/FN/TN, `recall = TP / (TP + FN)`, `precision = TP / (TP + FP)` и `mean_timecode_error_sec`. При нулевом знаменателе метрика равна 0. Ошибка таймкода — среднее абсолютное расстояние от размеченного события до ближайшего предсказанного, **только на TP-видео**; без TP это `null`. Также выводится число видео, вошедших в среднее. Пропуски отражаются в recall, а не в ошибке таймкода.

Это оценка наличия нарушения на уровне видео. Она не проверяет правильность `type` и нормативной ссылки, не сопоставляет все события в многособытийной записи и не измеряет скорость. Эти проверки добавляем отдельно и включаем в отчёт.

Повреждённые файлы/ошибки пайплайна завершают оценку с ненулевым кодом, чтобы не считать ошибку обработки отрицательным предсказанием. API-таймаут к прямому запуску eval не применяется. DummyPipeline на всех валидных видео предсказывает нарушение, поэтому его метрики отражают поведение заглушки.

## 14. Docker и работа без интернета

Образ основан на `nvidia/cuda:12.6.3-runtime-ubuntu24.04`; Python 3.11 копируется из официального образа Python. Зависимости и системные библиотеки устанавливаются **во время сборки**.

Сначала скопируйте `.env.example` в `.env` и замените `API_KEY` своим ключом. Команда копирования: `cp .env.example .env` в Bash или `Copy-Item .env.example .env` в PowerShell. Затем:

```bash
docker build -t cashier-violation-detector .
docker run --rm -p 8000:8000 --env-file .env \
  -v cashier-data:/app/data cashier-violation-detector
```

В PowerShell выполните `docker run` одной строкой: символ `\` из примера используется для переноса строк в Bash. Значение `DATA_DIR=data` из `.env.example` в контейнере разрешается в `/app/data`, поскольку рабочий каталог приложения — `/app`. Для будущего GPU-пайплайна добавьте `--gpus all` при наличии драйвера и NVIDIA Container Toolkit. DummyPipeline работает на CPU и GPU не требует.

После сборки сервис не скачивает ничего и не вызывает внешние API; модели для заглушки не нужны, `HF_HUB_OFFLINE=1` включён. Можно проверить полную сетевую изоляцию через `docker run --network none ...`, но тогда веб-интерфейс недоступен с хоста; API можно проверить командой Python внутри контейнера через `docker exec`. Веса будущей модели нужно заранее добавить в образ или смонтировать локально (например, `-v /path/to/models:/app/models:ro`), затем запускать без загрузок. Сам флаг Hugging Face не блокирует произвольный сетевой код будущего пайплайна.

Контейнер работает от пользователя UID 10001. При bind mount каталог данных должен быть доступен ему на запись. Именованный volume из примера сохраняет результаты между перезапусками.
