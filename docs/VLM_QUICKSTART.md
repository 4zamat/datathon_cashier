# Быстрая проверка событий готовой локальной VLM

**Обновление после v2:** GPU-запуск `20261018-055256` завершил генерацию всех шести ответов. Два результата отклонены за более чем три ссылки на кадры. Текущее исправление и команды установки находятся в `docs/VLM_FORMATFIX.md`; новый архив называется `brev-vlm-v2fix.zip`. Инструкции v2 ниже сохраняют контекст первоначального запуска. После исправления формата сохранённые ответы дают F1=0.667 на шести примерах, но ошибки событий, нормативного вывода и доказательств не устранены. Это не проверка готовой системы.

ResNet v4 не показал перенос распознавания действий между ракурсами. Этот прототип использует **Qwen3-VL-4B-Instruct** без дообучения. В smoke v1 от `20261018-054258` модель обработала 6 видео за 18–22 секунды каждое, но выдала одинаковый пустой отрицательный шаблон для всех: TP=0, FN=3, TN=3, FP=0. Этот результат не пригоден для детекции.

**Подход v2.** Сначала модель описывает видимые действия без классификации, затем по тем же кадрам оценивает пять типов событий. Из промпта удалён готовый ответ «всё нормально», непустое визуальное объяснение обязательно для каждой категории. Перед видео выполняется контроль на двух синтетических цветных изображениях и проверяются тензоры/токены изображений. Контроль на GPU прошёл, одинаковые пустые ответы больше не повторяются; семантические ошибки остались. Разметка, выбор шести видео, веса, разрешение и частота выборки не изменены. Промпт изменён после просмотра ошибок, поэтому это разработка, а не независимый тест.

Источник модели и лицензия Apache 2.0: https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct
Зафиксированная ревизия: `ebb281ec70b05090aa6165b016eac8ec08e71b17`.

## 1. Один раз загрузить веса на Brev

На Ubuntu для Triton также нужен системный C-компилятор. Первый smoke-запуск `vlm-v1-smoke-20261018-053647` загрузил модель, но все шесть вызовов остановились на `Failed to find C compiler`; качество не измерено. Установить один раз:

```bash
sudo apt-get update
sudo apt-get install -y build-essential
```

Если build-essential уже установлен, этот шаг пропустить. Веса повторно скачивать не нужно. Нули метрик в первом неудачном архиве не являются результатами предсказаний: `scored=0`, `errors=6`. Текущий код проверяет компилятор до загрузки модели и возвращает `null` для метрик, когда оценённых ответов нет; ранее отправленные архивы не перезаписаны.

В открытом терминале Brev, из проекта. Используется уже установленный CUDA torch; он не переустанавливается этим файлом зависимостей.

```bash
cd ~/workspace/datathon_cashier
.venv/bin/python -m pip install "transformers==4.57.6" "accelerate==1.12.0" "huggingface-hub==0.36.0" "Pillow==12.0.0"
HF_HUB_OFFLINE=0 .venv/bin/python -c "from huggingface_hub import snapshot_download; snapshot_download('Qwen/Qwen3-VL-4B-Instruct', revision='ebb281ec70b05090aa6165b016eac8ec08e71b17', local_dir='models/qwen3-vl-4b', allow_patterns=['*.json','*.safetensors','*.txt','README.md'])"
```

Скачивается около **8.9 GB на сервер Brev**, не на ноутбук. Отправки банковских видео в Hugging Face нет. Уже скачанные файлы повторно не скачиваются. На этой стадии нужен интернет для пакетов и весов. Сам анализ использует локальные веса; `local_files_only=True`, `trust_remote_code=False`, переменные offline и блокировка Python socket-соединений в диагностическом процессе.

## 2. Загрузить маленький архив и запустить шесть видео

Загрузить `brev-vlm-v2.zip` в `~/workspace/datathon_cashier/`. Видео уже в `data/videos`, повторная отправка не нужна. Ветку переключать не надо; код распаковывается в отдельную папку. Установленные для v1 библиотеки и модель подходят без переустановки.

```bash
cd ~/workspace/datathon_cashier
.venv/bin/python -m zipfile -e brev-vlm-v2.zip .
CC=/usr/bin/gcc CXX=/usr/bin/g++ .venv/bin/python -u brev-vlm-v2/scripts/run_vlm_brev.py --data-dir data --scope smoke
```

Будут проверены пары **Х-4/Х-5, Х-26/Х-27, Х-40/Х-43**: три положительных и три отрицательных примера из разных ракурсов. Проверяются также хэши исходных видео и обоих файлов весов. Модель загружается один раз и остаётся в GPU-памяти на время диагностического прогона.

Нагрузка ограничена: не более 20 кадров по всей длительности, не более 393216 пикселей на кадр, SDPA, BF16. Две генерации: наблюдение до 600 токенов и оценка до 1400, каждая с мягким лимитом 100 секунд (не заменяет жёсткий таймаут API). Текст содержит реальные времена кадров, но не имена файлов, старые предсказания, пользовательские комментарии или эталонные интервалы. Передаются кадры как последовательность изображений; это не нативный video-token режим. Короткое событие между кадрами может быть пропущено. Разрешение по времени явно записывается в отчёт. Хэши кадров, размеры тензоров и число image-токенов сохраняются для проверки ввода. Успех цветового контроля подтверждает лишь элементарную работу изображения, не распознавание банковских действий.

## 3. Передать результат

Прислать файл из строки **`ZIP (send this)`**. В нём результаты, оба сырых ответа каждого вызова, `vision_control.json`, ошибки, реальные обзорные JPEG даже для отрицательных ответов, HTML, конфигурация и снимок кода; весов и исходных видео в архиве нет. Можно сначала прислать маленький `METRICS`.

`COMPLETE=True` означает завершение выбранных вызовов без технических ошибок, а не хорошее качество. Прототип не получает автоматического разрешения на использование в рабочей системе. Проверить:

1. Находит ли он реальное действие и его тип, а не просто угадывает метку видео.
2. Не помечает ли положительными нормальные записи из каждой пары.
3. Соответствуют ли описания приложенным кадрам и времени.
4. Сколько ответов неопределённые или технически невалидные; они не скрываются под «нет нарушения».
5. Укладывается ли время анализа с загрузкой модели в 270 секунд на видео.

Пары выбраны для диагностики известных ошибок. Успех на шести видео не является итоговым качеством. Следующий прогон тем же неизменным промптом на всех 20 размеченных видео:

```bash
CC=/usr/bin/gcc CXX=/usr/bin/g++ .venv/bin/python -u brev-vlm-v2/scripts/run_vlm_brev.py --data-dir data --scope reviewed
```

`--scope all` дополнительно выдаёт наблюдения по 20 спорным роликам, но не присваивает им эталонные метки и не включает их в бинарные метрики. Не менять метки ради ответов модели. Изменение промпта после просмотра отчёта — новый эксперимент, а не исправление прежних показателей.

## Готовый адаптер к API

В архиве есть FastAPI и `pipeline.vlm:LocalVlmPipeline`. Публичный JSON использует только четыре уже проверенных типа из `rules/rules.yaml`. `rule.document` и `rule.clause` добавляет сервер из YAML; модель не пишет их сама.

Наблюдение `cash_left_unattended` сохраняется как визуальный кандидат. Само по себе оно не доказывает происхождение денег для конкретного пункта правил. Если есть только неподкреплённый нормативной категорией кандидат или неопределённость, адаптер возвращает ошибку для ручной проверки; он не выдаёт ложное «нарушений нет». Ошибки JSON и ссылки модели на несуществующие кадры также отклоняются.

После проверки реальных ответов можно запустить отдельный API из папки пакета:

```bash
cd ~/workspace/datathon_cashier/brev-vlm-v2
export VLM_MODEL_DIR="$HOME/workspace/datathon_cashier/models/qwen3-vl-4b"
export PIPELINE_CLASS="pipeline.vlm:LocalVlmPipeline"
export HF_HUB_OFFLINE=1
export API_KEY="ЗАДАЙ-СВОЙ-СЛУЧАЙНЫЙ-ДЛИННЫЙ-КЛЮЧ"
../.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

Воркера, авторизацию, удаление загруженного файла и жёсткий таймаут 270 секунд сохраняем. API пока использует отдельный дочерний процесс на задание, поэтому веса загружаются заново для каждого API-видео; время диагностического прогретого вызова не равно времени API. Скрипт probe измеряет загрузку отдельно. GPU-проверка полного API и Docker с этой моделью ещё не проведена. Основной Dockerfile по-прежнему содержит базовый сервис; этот эксперимент не заявляет готовность GPU Docker-образа.

Локально проверяются обработка ответов, реальные кадры, временные ссылки, справочник правил, исключение неопределённости и метрики покрытия. Реальная генерация Qwen выполняется на L4, где уже установлен torch.
