# Запуск сервиса на существующей Brev L4

Это запуск FastAPI с локальной Qwen3-VL-4B и веб-страницей. Нового обучения,
установки пакетов и скачивания весов не требуется. Используется существующая `.venv`.
Архив `brev-service-v1.zip` содержит код и правила, без видео, весов и API-ключей.
Распаковывается в отдельную папку; прежние эксперименты сохраняются.

## Запуск непосредственно из Git-репозитория

Код текущего сервиса также находится в ветке `fix/experiment-rules-handoff`.
В подготовленном GPU-окружении с весами `models/qwen3-vl-4b` выполнять из корня репозитория:

```bash
.venv/bin/python -u scripts/serve_vlm.py
```

Во втором терминале, после появления `Uvicorn running`:

```bash
.venv/bin/python -u scripts/check_live_api.py
```

Проверяющему скрипту нужны приватные видео в `data/videos`; для запуска самого
сервиса они не нужны. Зависимости и получение весов описаны в
[VLM_QUICKSTART.md](VLM_QUICKSTART.md#1-один-раз-загрузить-веса-на-brev).
Команды ниже относятся к ранее переданному отдельному архиву и сохраняются
для уже запущенной машины. Не запускайте второй сервер на занятом порту 8000.

Внешний адрес текущей машины: `http://global.prd.ga.run.brev.nvidia.com:24698`.
Проверены доступ страницы, `/health` и ответ 401 без API-ключа из внешней сети.
Это не заменяет полного прогона качества или авторизованной загрузки через этот адрес.

## 1. Первый терминал: сервер

Загрузить архив в `~/workspace/datathon_cashier` через Jupyter. Выполнить:

```bash
cd ~/workspace/datathon_cashier
.venv/bin/python -m zipfile -e brev-service-v1.zip .
CC=/usr/bin/gcc CXX=/usr/bin/g++ .venv/bin/python -u brev-service-v1/scripts/serve_vlm.py
```

Дождаться `Uvicorn running on http://0.0.0.0:8000`. Оставить терминал открытым.
Скрипт проверяет CUDA, компилятор, контрольные суммы кода и весов, затем запускает
сервер. Веса загружаются при первом задании. Проверка сумм не означает проверку
качества модели. `API_KEY`, если задан в окружении, имеет приоритет; иначе ключ
генерируется один раз в `data/service_v1/api-key.txt` с правами 0600.

## 2. Второй терминал: проверка через настоящее API

```bash
cd ~/workspace/datathon_cashier
.venv/bin/python -u brev-service-v1/scripts/check_live_api.py
```

Проверяются 401 без ключа и с неправильным ключом, загрузка multipart, опрос,
схема JSON и реальные JPEG-кадры. Последовательно отправляются все шесть прежних
диагностических видео: 4, 5, 26, 27, 40, 43. Имена исходных файлов модели не
передаются. Выборка не является независимым тестом качества.

В конце появится `SEND THIS ZIP: .../data/exports/api-service-v1-....zip`.
Скачать этот ZIP: в нём ответы API, длительности и исходные ответы модели.
Результаты и отказы не маскируются. Если `status=failed`, вердикт в API-заглушке
не означает отсутствие нарушения. Код выхода 1 означает, что хотя бы одно
задание не завершилось автоматическим вердиктом.

Для повторной проверки одного файла после исправления можно указать `--numbers 27`.
Это проверка отдельного случая, не новая оценка общей точности.

## 3. Веб-страница

В Brev открыть машину → Access → HTTP Ports → добавить порт назначения 8000.
В варианте интерфейса с Using Tunnels добавить 8000 там. Открыть выданный URL.
Ключ для ввода на странице посмотреть в отдельном терминале:

```bash
cat ~/workspace/datathon_cashier/data/service_v1/api-key.txt
```

Если сервер использует ранее заданный `API_KEY`, вводить именно его.
Ключ не включать в архивы, Git и скриншоты. Страница и API работают на одном сервере.
MOV показывается, если браузер поддерживает его кодек; иначе исходник открывается
в VLC, а изображения результатов остаются доступны на странице.

HTTP-ссылка Brev может требовать входа в аккаунт. Для жюри нужно отдельно проверить
внешний доступ: без ключа оба API должны вернуть 401, с ключом GET неизвестного
задания — 404, а не страницу входа Brev. При необходимости настроить TCP-порт
8000 через консоль и использовать фактический адрес/порт, который выдала Brev.
Нельзя считать адрес сдаваемым, пока внешние запросы не проверены.
Документация: https://docs.nvidia.com/brev/cli/connectivity

## Что изменилось и что ещё не доказано

- Устранён отказ из-за 4–12 ссылок на кадры: проверяются все ссылки, затем выбираются 1–3.
- Для предложенных нарушений модель дополнительно проверяет обязательные видимые
  условия. Один уход сотрудницы недостаточен для пункта 22. Для личных вещей
  нужен кадр размещённой вещи; время события выбирается по этому условию.
- Это дополнительная модельная проверка, а не гарантия правильной квалификации.
  Новые предсказания необходимо проверить на GPU. Старые метрики ей не приписываются.
- Сомнение без подтверждённого нарушения даёт `failed` с сообщением о ручной проверке.
  Это ограничение автоматизации и потеря покрытия, не успешный ответ по качеству.
- 20 равномерных кадров могут пропустить короткое действие; прежний пропуск
  денег предыдущего клиента не объявляется исправленным.
- Веса работают локально, `local_files_only=True`, HF/Transformers offline включены.
  Никакого внешнего AI API в сервисе нет.
- Один воркер, отдельный завершаемый процесс на видео, лимит 270 секунд с очередью,
  удаление загруженного видео и сохранение JSON. Исходный `data/videos` не меняется.
- `/health` подтверждает доступность сервера и конфигурацию; успешный реальный
  инференс подтверждается только завершённым заданием.

Диагностика лежит в `data/service_v1/diagnostics`, задания — в
`data/service_v1/jobs_runtime/jobs`. Она может содержать описания частных видео.
После запуска ещё нужны: проверка шести ответов, внешний URL/API-ключ для жюри,
финальная проверка Docker и комплект сдачи. Этот пакет не объявляется готовой
производственной системой.
