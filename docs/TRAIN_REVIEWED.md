# Короткий эксперимент v3 после ручной проверки

Цель: проверить, помогает ли временной контекст и интервальная разметка предсказывать бинарную метку датасета. Это не готовый классификатор статей регламента. Веса энкодера ResNet18 заморожены; обучается небольшая линейная модель поверх текущего кадра, среднего за пять кадров и изменения признаков за это окно. Частота — 2 кадра/с.

## Что исправлено в данных

- Исходные видео, `labels.csv` и человеческие наблюдения сохраняются. Согласование находится отдельно в `data/annotations/reconciled_v3/`.
- Все события имеют группы похожих дублей/сценариев. Более широкие группы расстановки оборудования целиком закреплены за одной частью train/val/test.
- Точные дубли представлены одним видео. Разные таймкоды внутри одного продолжающегося события не считаются разными бинарными классами.
- Спорные наблюдения не становятся подтверждёнными отрицательными кадрами. Для бинарного эксперимента исходные положительные метки организаторов, не получившие достаточного подтверждения, сохраняются как **слабая разметка с пониженным весом**. Это не превращает их в юридически подтверждённые нарушения.
- Обычные интервалы внутри положительных видео используются как отрицательные примеры; интервалы положительных событий имеют приоритет при пересечении. Неотмеченные фрагменты положительного видео игнорируются.
- Области проверки объектов не используются как метки нарушений. Этот запуск не обучает YOLO и не читает рамки оборудования.

`events.csv` — согласованные события; `event_review.csv` сохраняет исходную формулировку, решение и причину. `human_observations.json` — снимок исходных документов. `review_decisions.json` фиксирует все решения. В `dataset_manifest.json` находятся точные интервалы, веса, разбиение и SHA-256 видео. `summary.json` содержит количества и нерешённые вопросы.

## Запуск из небольшого архива на Brev

Ожидается существующая папка проекта с `.venv`, рабочими Torch/torchvision, исходными `data/videos` и локальным энкодером от v2. Повторно загружать видео, устанавливать библиотеки или скачивать веса не требуется.

Загрузить приватный `brev-reviewed-v3.zip` в папку проекта через файловую панель Jupyter, затем в её терминале:

```bash
cd ~/workspace/datathon_cashier
source .venv/bin/activate
python -m zipfile -e brev-reviewed-v3.zip .
python -u brev-reviewed-v3/scripts/run_reviewed_brev.py --data-dir data
```

Архив распаковывается в отдельный `brev-reviewed-v3/`; исходники основного проекта не заменяются. Запуск сверяет хэши пакета и видео. Пустой/несовпадающий файл вызывает ошибку до обучения. Новый каталог результатов имеет время запуска в имени; предыдущие результаты не перезаписываются.

Энкодер ищется среди `models/*/encoder_resnet18.pt`, затем `data/imports/*/model/encoder_resnet18.pt`. Если ни одного нет, передать `--encoder-weights путь/encoder_resnet18.pt`. Никаких автоматических скачиваний. CUDA обязательна по умолчанию; явный `--device cpu` — отдельный вариант для диагностики.

В репозитории без архива:

```bash
python scripts/run_reviewed_brev.py --data-dir data --dataset data/annotations/reconciled_v3/dataset_manifest.json
```

## Как проходит запуск

1. Проверка входных видео, непересечения групп и обоих классов.
2. Извлечение признаков только train/val и подбор трёх значений регуляризации по validation loss.
3. Выбор порога только по полным validation-видео. Test не участвует в выборе параметров.
4. Сохранение весов и повторная загрузка для оценки полных видео; расчёт precision/recall/F1, матрицы ошибок, отклонения от исходного таймкода и расстояния до размеченного интервала.
5. Проверка совпадения результата в новом процессе с заблокированной сетью на одном test-видео. Это проверка воспроизводимости, не качества.
6. HTML с кадрами ошибок/совпадений и приватный архив результатов.

## Где результат

В конце напечатаются полные пути:

- `data/exports/reviewed-v3-ДАТА-ВРЕМЯ.metrics.json` — небольшой отчёт, его передать первым;
- `data/exports/reviewed-v3-ДАТА-ВРЕМЯ.zip` — модель, метрики, предсказания, разбиение, исходники, входные аннотации и контрольные суммы;
- `data/runs/reviewed-v3-ДАТА-ВРЕМЯ/review.html` — автономный визуальный отчёт, можно скачать и открыть локально;
- `data/runs/reviewed-v3-ДАТА-ВРЕМЯ.log` — журнал.

`COMPLETE: True` означает успешный запуск, сохранение и offline reload, но не высокое качество. При ошибке создаётся частичный архив с `complete:false`; выводить его как успешный результат нельзя. Не выключать машину до скачивания и проверки архива.

## Как оценивать честно

Все исходные ролики уже изучались командой: test здесь — **development holdout**, не новая независимая проверка. Не выбирать следующую настройку по его ошибкам. Числа нельзя прямо сравнивать с v2: изменились группы, интервалы и число примеров. Рядом считается baseline «всегда нарушение». Если модель хуже него, фиксируем неудачный эксперимент, не заявляем улучшение.

Уверенный ответ API с типом нарушения и правилом потребует отдельной проверки наблюдаемого действия и применимости нормы. Бинарный score v3 сам по себе этого не обеспечивает. `personal_items_in_cash_area`, `previous_cash_not_stored` и другие статьи нельзя приписывать пику score без классификации события.

## Повторная подготовка

Для новой версии решений выбрать новый выходной каталог:

```bash
python scripts/prepare_reviewed_dataset.py --decisions path/to/review_decisions.json --out-dir data/annotations/reconciled_v4
python scripts/validate_annotations.py --events data/annotations/reconciled_v4/events.csv
python -m unittest tests.test_reviewed_training -v
```

Нужные для юридического завершения сведения перечислены в `summary.json`: прежде всего внутренние требования к блокировке компьютера, доступу, ключам и документам. Они не блокируют этот диагностический запуск, но ограничивают допустимые выводы о нарушениях.
