# Отдельные задания команды и порядок слияния

База для работы сейчас: **`fix/experiment-rules-handoff`**. Она включает эксперимент ноутбука и исправления. Старую ветку `experiment/laptop-baseline` сохраняем как историю первого результата. Интегратор — Азамат. Перед началом впишите одного исполнителя на каждую роль; один человек может взять несколько ролей последовательно.

Общая цель следующего этапа: воспроизводимый эксперимент, проверенные наблюдения и рабочая демонстрация. Первый ResNet дал test TP=3, FP=4, FN=1, TN=0; это ещё не детектор банковских действий. Новые правила сами по себе качество модели не улучшают.

## Как создать свою ветку

Если проект уже склонирован, повторно клонировать не нужно. Из его папки:

```bash
git status --short
git fetch origin
git switch -c team/ui origin/fix/experiment-rules-handoff
```

В последней строке заменить `team/ui` на свою ветку из таблицы. Если есть незакоммиченная работа, сначала сохранить её в собственной ветке. Не делать `reset --hard`, `clean`, принудительный checkout или force push. Если ветка уже создана, использовать `git switch team/ui`.

После работы: проверить `git diff`, добавить только свои конкретные файлы, сделать commit и `git push -u origin team/ui`. Создать PR с **base `fix/experiment-rules-handoff`** и своей head-веткой. Если базу уже объединили в `main`, интегратор меняет base всех PR на `main` и сообщает команде. Не создавать несколько независимых веток с одним названием.

В описании PR: что изменено, как запустить/проверить, фактический результат проверок, ограничения. Приватный архив передаётся отдельно по согласованному каналу, рядом — SHA-256 и commit. Не добавлять `data/`, `models/`, кадры банковских видео, ключи и `.env` даже через `git add -f`.

## Кто какими файлами владеет

| Исполнитель | Ветка | Разрешённые изменения в Git | Отдельные приватные результаты |
|---|---|---|---|
| Дизайн | `team/ui` | `static/*`, `docs/ui_acceptance.md` | При необходимости запись демонстрации на синтетическом видео |
| Разметка | `team/annotations` | `docs/annotation_handoff.md` | `data/annotations/v1/events.csv`, `scene_groups.csv`, `disputes.csv` |
| Нормативы | `team/rules-review` | `rules/proposals/*`, `docs/rules_review.md` | Примеры спорных эпизодов, без публикации кадров в Git |
| ML | `team/ml-v2` | `experiments/event_baseline/*`, `reports/event_baseline_v1.md`, `requirements-ml-event.txt` | Веса, конфигурация, сплиты, предсказания, журналы и архив |
| Проверки | `team/qa` | `tests/test_acceptance_extra.py`, `docs/acceptance.md` | Журналы прогонов с приватными видео |
| Азамат / интеграция | общая ветка | `app/*`, `pipeline/*`, `scripts/*`, `rules/rules.yaml`, общие зависимости, Dockerfile, README | Версия общего датасета и финальные сборки |

Эта таблица — граница работы, чтобы не редактировать один файл одновременно. Нужное изменение чужого файла описывается в PR; интегратор переносит его после согласования. Проверяющий может сообщить о баге в любом модуле.

## Задание 1 — интерфейс и дизайн

**Можно начинать сразу, без обученной модели.** Сохранить HTML/CSS/JS без фреймворков и один сервер FastAPI.

1. Оформить страницу в согласованном стиле ForteBank. Если официальных цветов/логотипа нет, использовать предоставленные командой материалы; не объявлять приблизительные цвета официальным брендбуком.
2. Сделать выбор `.mov`, имя/размер файла, поле API-ключа, кнопку запуска, понятные состояния загрузки и ожидания. Запретить повторное случайное отправление, пока идёт запрос.
3. POST `/api/v1/analyze` с multipart-полем `file`; GET `/api/v1/jobs/{job_id}` каждые 2 секунды. Заголовок `X-API-Key` у обоих запросов. Ключ только в памяти страницы, не в URL, консоли или localStorage.
4. Отобразить `done/violation`, `done/no_violation`, `processing` и `failed`. При `failed` не показывать зелёное «нарушений нет». Прогресс до получения этапов от сервера — неопределённый, без выдуманных «детекция 70%».
5. Добавить локальный видеоплеер через выбранный файл (`URL.createObjectURL`), переход к таймкоду из карточки, освобождение object URL при замене файла. MOV с неподдерживаемым браузером кодеком может анализироваться сервером: показать понятное сообщение, не считать это ошибкой модели.
6. Карточка: тип, время, описание, 1–3 JPEG из base64, `rule.document` и `rule.clause`. Пользовательские строки вставлять через `textContent`, а не как HTML. Ошибки 401/413/415 и разрыв сети должны быть понятны; не запускать новый анализ для простого повтора опроса.

**Сдать:** PR, `docs/ui_acceptance.md` с шагами проверки и скриншотами на синтетическом видео для пяти состояний. Не трогать API, ML, Streamlit и формат JSON. Для реального сервера точка входа — `app.main:app`; `/health` сейчас не существует.

## Задание 2 — просмотр и разметка

**Можно начинать сразу.** Видео и их имена не переименовывать. Исходные `data/raw/open_labels.xlsx` и `data/labels.csv` сохранить. Латинская `X` и кириллическая `Х` различаются: копировать путь из нашего CSV.

1. Просмотреть **все 42 имеющихся видео**, включая 20 исходно отрицательных. Не создавать отсутствующие X-6/7/9/36/41/42 и не считать их отрицательными. Для экономии времени сначала спорные пары и отрицательные примеры, затем остальные.
2. Скопировать заголовки из `templates/events.csv` в `data/annotations/v1/events.csv`. Одна строка — одно наблюдаемое событие/интервал. Время — секунды с точкой, от начала файла; текст с запятой заключать в CSV-кавычки.
3. Поля: точный `video`; уникальный внутри видео `event_id`; `start_sec`/`end_sec`; кандидат `event_type`; буквально видимое `observation`; `assessment`; имя `reviewer`; `scene_group_id`.
4. Допустимые типы: четыре категории из `rules/rules.yaml`, `normal`, `unknown`. Оценка: `possible_violation`, `no_violation`, `uncertain`. Сначала «кассир ушёл из рабочей зоны, клиент остался», отдельно — кандидат п. 22. Не писать «украл» по перекладыванию денег.
5. Для целиком просмотренного нормального ролика — строка `normal/no_violation` с интервалом просмотра. Для сомнений — `uncertain`, описать причину и нужный контекст. Невидимое действие не равнозначно отсутствующему действию.
6. Заполнить `scene_groups.csv` по `templates/scene_groups.csv`: **ровно одна строка на исходное видео**, общий ID для одной сцены/записи, её обрезок, повторов и перекодированных копий. Для явно одной постановки в том же сеансе использовать общую группу; просто одинаковый стол ещё не доказывает дубль. При сомнении — `uncertain` и причина. Статусы `include/exclude/uncertain`; два последних исключаются из следующей обучающей выборки.
7. Проверить Х-4/Х-47: побайтово одинаковое видео, но времена 57/68 секунд. Возможно два события — нужно записать оба и решение проверяющих. Сейчас оба консервативно исключаются. Х-5/Х-48 — одинаковое отрицательное видео, один представитель. Другие пары «по сути одно видео, но разные метки» перечислить отдельно с обоими интервалами и сравнением отличий.
8. `disputes.csv`: `video_a,video_b,start_a,end_a,start_b,end_b,issue,reviewer_1,reviewer_2,decision`. Два человека независимо смотрят спорные события. Не исправлять исходную метку единолично; сохранить исходную, предложенную и причину в передаче интегратору.

У Азамата также подготовлен маленький приватный `data/exports/annotation-starter-v1.zip` с точными именами и длительностями 42 файлов. Распаковать в корень проекта, скопировать `data/annotations/starter_v1/` в `data/annotations/v1/`. Это черновик: все строки пока `uncertain`, поля наблюдения и проверяющего пусты. Его нельзя считать выполненной разметкой; валидатор потребует заполнения. Начальные группы объединяют только побайтовые дубли.

Проверка формата (из корня):

```bash
python scripts/validate_annotations.py --events data/annotations/v1/events.csv
```

Для незаконченной работы добавить `--allow-partial`; финальная сдача — без него. Скрипт проверяет имена, интервалы, типы и покрытие, но не доказывает правильность человеческого наблюдения.

**Сдать:** приватный ZIP только с тремя CSV, числом просмотренных видео/неразрешённых споров и SHA-256; PR с `docs/annotation_handoff.md` без содержимого приватных записей. Видео повторно не слать. Если разметчиков двое, разделить список видео по строкам исходного CSV и сдать отдельные `events_<имя>.csv`; ответственный объединяет их и проверяет полное покрытие. Неразрешённый спор не превращается в уверенную метку.

## Задание 4 — ML, два последовательных результата

**Сначала сохранить ноутбук:** `docs/EXPERIMENT_RUNBOOK.md`, раздел о передаче артефактов. Потом запуск.

**Результат A, можно сейчас:** один диагностический запуск исправленного бинарного baseline на имеющихся метках по runbook. Никаких изменений raw-данных. Новые каталоги v2, отдельный smoke, настройки выбираются только по validation. Отчёт сравнивает с прежними числами и «всегда нарушение». Он не объявляется проверкой новых ракурсов; сходство сцен ещё требует ревизии.

**Результат B, после согласованной разметки:** выбрать 1–2 категории с достаточными положительными и похожими отрицательными примерами. Зафиксировать гипотезу до просмотра test. Например, уход кассира при продолжающемся обслуживании: нужна последовательность присутствия кассира/клиента, а не классификация одного кадра. Сначала простой локальный детектор людей + временное правило; объект «деньги» не считать готовым классом любой предобученной YOLO. Если нужен детектор денег/лотка, отдельно выдать список нужных кадров для рамочной разметки и формат экспорта. Не тратить время команды на рамки всех объектов заранее.

Код нового опыта хранить в `experiments/event_baseline/`, иметь CLI `--video <path>` без истинной метки в аргументах/имени-зависимой логике. Обучение, порог и преобразования не использовать из test. Сцены не пересекаются между частями. Если групп не хватает — сообщить это, а не разделять кадры одного ролика случайно.

**Сдать:** PR с кодом, отдельными зависимостями и отчётом; приватный архив с весами, настройками, точными CSV разбиения, построчными предсказаниями, журналом обучения, версиями ПО и хэшами. Отчёт: TP/FP/FN/TN, precision/recall/F1, ошибка времени только на TP, ошибки обработки, холодный запуск вместе с загрузкой модели, RAM/VRAM, сравнение с константами, ограничения. Проверка сохранения/загрузки обязательна. Бинарный класс «нарушение» не переименовывать автоматически в конкретную статью.

## Задание 5 — независимая проверка

1. На чистом клоне установить service/dev-зависимости, выполнить `python -m unittest discover -s tests -v`.
2. Проверить API с правильным/неправильным/отсутствующим ключом, `.mov` около 30 МБ, пустым и повреждённым файлом, несколькими задачами, рестартом и таймаутом. Не менять таймаут больше 270 с.
3. Проверить Docker-сборку, CPU Dummy без интернета и доступность API с другого компьютера в согласованной сети. Приватные данные не включать в образ.
4. После появления реальной модели повторить холодный анализ в текущем процессе на каждое видео: таймаут включает запуск процесса и загрузку весов. Офлайн-проверка должна блокировать сеть, одного `HF_HUB_OFFLINE=1` недостаточно.
5. Сопоставить JSON с утверждённым организаторами контрактом. Наш исходный контракт содержит `rule` и `error`; пример в кейсе может отличаться. Не удалять поля самостоятельно: зафиксировать конкретное расхождение и получить решение интегратора/организаторов.

**Сдать:** PR с воспроизводимыми тестами на синтетических данных и `docs/acceptance.md`: ОС, commit, команды, что прошло, что не проверено, точные ошибки. Не считать тест Dummy подтверждением качества ML.

## Порядок merge и следующие действия Азамата

1. Принять эту базу исправлений. Забрать архив ноутбука и проверить хэши на своём компьютере.
2. UI и независимые тесты можно принимать параллельно с разметкой — у них отдельные файлы.
3. Принять юридическую проверку; изменения каталога перенести централизованно, сохранив согласованные типы.
4. Проверить CSV разметки, спорные пары и создать новую версию разбиения. Старые labels/splits не перезаписывать. Приватные CSV не «merge в Git»: они передаются как версия датасета с хэшами.
5. Принять ML-код только с результатами и артефактами. Подключить в `pipeline/real.py` лишь категории, которые реально распознаются и проверены; сервер добавляет норму из YAML.
6. Перед слиянием каждого PR: `git diff`, тесты затронутого модуля, отсутствие данных/секретов, просмотр владельцем. Конфликты общих файлов решает интегратор. После подключения модели — полный end-to-end и офлайн-прогон в Docker.

План не требует ждать разметку, чтобы запустить результат A. Но повышение recall бинарного baseline не доказывает готовность нормативного детектора: итоговая приёмка также проверяет тип события, обоснование, кадры и ложные тревоги.
