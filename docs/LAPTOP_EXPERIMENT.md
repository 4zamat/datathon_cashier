# Первый ML-эксперимент на ноутбуке

## Цель

Проверить, может ли небольшая локальная модель находить признаки нарушения на доступных видео, насколько она ошибается и сколько времени занимает анализ. Результат первого эксперимента — воспроизводимые измерения, код и сохранённая модель.

Сейчас в репозитории работает `DummyPipeline`. Обучающего скрипта и настоящей модели пока нет: их нужно реализовать в рамках этой задачи. Изменения выполняются в ветке **`experiment/laptop-baseline`**. `main` остаётся рабочей версией сервиса до проверки Pull Request.

## 1. Как открыть проект

Владелец репозитория предоставляет участнице команды доступ на запись, если его ещё нет. Не передавать пароль или токен владельца: GitHub используется под собственным аккаунтом.

```bash
git clone https://github.com/4zamat/datathon_cashier.git
cd datathon_cashier
git fetch origin
git switch --track origin/experiment/laptop-baseline
```

Если локальная ветка уже существует, вместо последней команды выполнить `git switch experiment/laptop-baseline`. Открыть **корневую папку `datathon_cashier`** в Claude Code.

Архив датасета передаётся участнице отдельно. Распаковать его в корень проекта: внутри архива уже есть папка `data/`. После распаковки должны существовать `data/videos/`, `data/labels.csv` и исходный Excel в `data/raw/`. Не создавать лишний уровень `data/data/`.

`labels.csv` — подготовленная копия исходной Excel-разметки для программы. Сохранять кириллические и латинские символы в именах файлов. В актуальном CSV пути уже сверены с видео; повторно заменять все `Х` на `X` не нужно.

## 3. Порядок эксперимента

### Шаг A. Окружение и короткая проверка

Целевой ноутбук по данным команды: **GeForce RTX 5060, Intel Core i5 13-го поколения, 16 ГБ RAM**. ОС, точную модель GPU, объём VRAM и версию драйвера проверить на месте. Для RTX 5060 Laptop NVIDIA указывает 8 ГБ видеопамяти; 16 ГБ RAM из описания ноутбука — отдельная системная память. [Спецификации NVIDIA](https://www.nvidia.com/en-us/geforce/laptops/50-series/).

Для RTX 5060 нужна сборка PyTorch с поддержкой Blackwell. Для актуальных версий, начиная с PyTorch 2.12, ориентироваться на CUDA 13.0+ и совместимый драйвер: NVIDIA 580.88+ для Windows или 580.65.06+ для Linux для сборки CUDA 13.0. При выборе другой версии сверять её матрицу совместимости. Не копировать старую команду установки CUDA 11.8/12.6 по умолчанию. [Изменения платформы в PyTorch 2.12](https://pytorch.org/blog/pytorch-2-12-release-blog/).

Первый запуск проводить непосредственно в Python-окружении ноутбука. Текущий Dockerfile сервиса ещё не подготовлен и не проверен для ML-нагрузки на RTX 5060; контейнеризацию модели выполнить после успешного локального эксперимента.

Начальные настройки эксперимента для этого ноутбука:

| Параметр | Начальное значение |
|---|---|
| Модель | ResNet18 с замороженными весами + линейный классификатор |
| Частота кадров | 2 fps, последовательное чтение |
| Вход энкодера | 224 × 224 с преобразованиями выбранных весов |
| Batch извлечения признаков | 16; при нехватке VRAM уменьшить до 8 или 4 |
| Загрузчики данных | Начать с `num_workers=0`; увеличение проверить отдельно |
| Хранение данных | Видео читать по одному, признаки кэшировать на диск |
| Обучение классификатора | До 20 эпох; ранняя остановка по validation, patience 5 |
| Питание | Запускать ноутбук от зарядного устройства |

Это начальные параметры, а не измеренная оптимальная конфигурация. Не загружать весь декодированный датасет в RAM. Скорость определить коротким прогоном на этом ноутбуке.

1. Определить ОС, архитектуру, CPU, объём RAM, наличие GPU и доступную память GPU. Проверить поддержку CUDA или MPS самим установленным PyTorch; при отсутствии использовать CPU.
2. Создать отдельное окружение `.venv` с Python 3.11. ML-зависимости зафиксировать отдельно в `requirements-ml.txt`, включая совместимые версии `torch` и `torchvision`. Не менять зависимости API без необходимости.
3. До полного запуска проверить чтение одного видео, загрузку энкодера, получение признаков, один шаг обучения и сохранение/загрузку весов. На Windows защищать запуск обучения блоком `if __name__ == "__main__"`.
4. Записать время короткой проверки и оценить длительность полного запуска. Целевой бюджет первого эксперимента — до 60 минут вычислений после установки зависимостей и скачивания весов. Это ограничение эксперимента, а не обещание скорости ноутбука. Если бюджет превышается, уменьшить объём первого прогона и явно указать это в отчёте; не представлять частичный прогон как завершённую оценку.

Для этого ноутбука сначала убедиться, что вычисления действительно выполняются на RTX 5060. Одного `torch.cuda.is_available()` недостаточно: выполнить GPU-операцию и обратное распространение ошибки. Если проверка падает, выяснить совместимость драйвера и сборки; переход на CPU явно отметить в отчёте.

```python
import torch

print("PyTorch:", torch.__version__, "CUDA build:", torch.version.cuda)
assert torch.cuda.is_available(), "CUDA is not available in this environment"
properties = torch.cuda.get_device_properties(0)
print("GPU:", properties.name, "VRAM GiB:", properties.total_memory / 1024**3)
print("Compute capability:", torch.cuda.get_device_capability(0))
x = torch.randn(256, 256, device="cuda", requires_grad=True)
(x @ x).square().mean().backward()
torch.cuda.synchronize()
print("CUDA forward/backward OK")
```

### Шаг B. Данные и разбиение

1. Проверить все пути из `data/labels.csv`, число строк, классы и границы таймкодов. Сопоставить результаты с `data/dataset_check.json`. Все исходные записи сохранить.
2. Посчитать SHA-256 видео. Объединить точные дубли в группы. Дополнительно объединить фрагменты одной исходной записи или явно связанной сцены, если такие связи известны. Не делить кадры одного видео между выборками.
3. В исходных данных есть дубли и группа одинаковых видео с разными таймкодами. Найти их по отчёту, не выбирать «правильный» таймкод автоматически. Для первого эксперимента исключить всю такую группу из обучения и оценки, сохранив её в локальном списке для уточнения разметки.
4. Для дублей с одинаковыми метками и таймкодами использовать один представитель, сохранив соответствие исходным файлам. Разделять по группам; считать метрики по уникальным видео.
5. Зафиксировать seed `42` и один набор разбиений примерно **60% train / 20% validation / 20% test** с представленностью обоих классов в каждой части. Если дополнительные группы мешают такому разбиению, выбрать ближайшее корректное и документировать причину. Списки сохранить в `data/splits/laptop_baseline/`.
6. Обучать параметры только на train. По validation выбирать порог, число эпох и остальные настройки. Test открывать для оценки после фиксации всех решений. Не подбирать параметры по результату test; если это уже произошло, честно считать эту часть дополнительной validation.
7. Не обучаться на всём датасете перед оценкой. Нормализацию признаков и другие обучаемые преобразования также подбирать только на train.

Размер набора небольшой, поэтому в отчёте нужны числа видео и TP/FP/FN/TN вместе с процентами. Один удачный результат на малом test ещё не подтверждает устойчивость на другом ракурсе.

Разделение связанных примеров по группам помогает избежать попадания похожих данных в обучение и проверку. [Документация scikit-learn о групповой кросс-валидации](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data).

### Шаг C. Небольшая обучаемая модель

Первый вариант: **предобученный ResNet18 как неизменяемый извлекатель признаков + небольшой бинарный классификатор**. Это конкретный стартовый вариант для сравнения, а не утверждение, что он оптимален для банковских действий. Проверить условия использования выбранных весов и сохранить их источник и версию. Такой подход к переносу обучения описан в [официальном руководстве PyTorch](https://docs.pytorch.org/tutorials/beginner/transfer_learning_tutorial.html).

1. Читать видео последовательно и выбирать кадры около 2 fps. Использовать реальные временные метки. Для некоторых MOV переход прямо к последнему кадру в OpenCV ненадёжен, а последовательное чтение работает.
2. Применять преобразования, соответствующие весам энкодера; сохранить их в конфигурации. Не обучать весь энкодер на первом прогоне. Признаки можно закэшировать в `data/features/`, чтобы повторно не декодировать видео при подборе классификатора.
3. Для положительных обучающих примеров использовать кадры в небольшом окне вокруг размеченного таймкода, начальный вариант — ±1 секунда. Это приближённая разметка события, а не подтверждённая метка каждого кадра. Для отрицательных примеров брать кадры из видео с меткой «без нарушения». Остальные кадры положительного видео не считать автоматически отрицательными.
4. Сбалансировать вклад видео, чтобы длинные записи не доминировали только из-за количества кадров. Ограничить размер batch под RAM/VRAM. Для первого варианта достаточно линейного классификатора поверх признаков.
5. При проверке обрабатывать **всё видео**, не используя размеченный таймкод для выбора входных кадров. Получать оценку по кадрам, фиксировать способ агрегации в оценку видео; начальный вариант — максимум. Предполагаемый таймкод — время максимальной оценки. Более сложное сглаживание добавлять только как отдельный измеренный вариант.
6. На validation выбрать порог по заранее зафиксированному правилу: максимальный F1, при равенстве — больший recall. Записать правило и выбранное значение. Не пересчитывать порог на test.
7. Для сравнения посчитать на тех же видео простые варианты «всегда нарушение» и «никогда нарушение». DummyPipeline не является моделью распознавания и не подтверждает качество обучения.

Этот эксперимент обучает наличие события и пробует локализовать его по времени. В исходных метках нет проверенной классификации банковских нарушений и нормативных пунктов; она остаётся отдельной задачей команды.

### Шаг D. Честная оценка

На фиксированном test вывести:

- Число видео, классов и исключённых групп; TP, FP, FN, TN; recall, precision и F1 по видео.
- Среднюю абсолютную ошибку таймкода только на верно найденных положительных видео и число таких видео. Если их нет — `null`, не ноль. Отдельно указать пропуски.
- Время подготовки признаков, обучения и полного анализа каждого test-видео. Измерять анализ без готового кэша признаков. Отдельно показать первый запуск с загрузкой модели и повторный запуск, указать оборудование.
- Среднее и максимальное время анализа, используемую память там, где её можно измерить, размеры весов и все ошибки обработки. Ошибки не считать нормальными отрицательными предсказаниями.
- Ограничения: маленький test, шум приблизительных кадровых меток, дубли, возможная зависимость от фона/ракурса и отсутствие оценки реальных типов нарушений.

Подробные предсказания с идентификаторами видео сохранить локально в `data/runs/laptop_baseline/predictions.csv`. Формат: `video,split,actual,predicted,score,true_timecode_sec,predicted_timecode_sec,elapsed_sec,error`. В публичный отчёт включать агрегаты, без кадров и исходной разметки.

Существующий `scripts/eval.py` ожидает `Pipeline -> Result` с типом события и кадрами. Для этого бинарного эксперимента можно добавить отдельный скрипт оценки и использовать те же определения метрик. Не подгонять ответ под API через выдуманный тип нарушения, демонстрационное правило или ложное юридическое обоснование. Адаптер для рабочего API подключим после согласования категорий.

## 5. Когда первый эксперимент считается выполненным

- Модель действительно обучалась, её предсказания получены на видео, которых не было в обучении и подборе настроек.
- Дубли и связанные фрагменты не пересекают выборки; конфликтующая разметка учтена явно.
- Есть измеренные качество и скорость, сравнение с простыми постоянными предсказаниями и описание ограничений.
- Веса загружаются в новом процессе, все команды воспроизводимы.
- Код и отчёт находятся в ветке, архив с весами и метаданными готов к передаче.

Низкие метрики тоже являются полезным результатом этого эксперимента. Они помогают решить, что нужно дальше: уточнить разметку, добавить временной контекст, собрать больше примеров или проверить другую модель. Большая GPU сама по себе не исправляет недостаток данных или ошибочную оценку.
